Firestore for Rust

Reads, joins and subqueries

This page lists what a SQL SELECT can read and how, from the FROM clause to joins and their cost. Setup, parameters and the read-only options are in SQL, and the results that differ from a SQL database in Query and write semantics.

Sources

The FROM clause names where the documents come from:

SourceReads
FROM books or FROM `books` a root collection; backticks hold an ID with hyphens or dots
FROM `restaurants/rest-01/reviews`the collection under a document
FROM collection_group('reviews')every collection with that ID, anywhere in the database
FROM documents('books/b1', 'books/b2')the documents at those paths, relative to the documents root; a path that names no document is left out
FROM database()every document of the database
FROM subcollection('reviews')the collection under the current document, inside a subquery or join
FROM (SELECT ..) AS ta derived table: the rows of another SELECT
FROM ctea common table expression

A table alias is written FROM books AS b. A name that is defined by WITH matches without regard to case, as a table alias does, and hides a collection of the same name.

Reads by ID

A WHERE on __name__, __name__ = 'book-01', __name__ IN ('book-01', 'book-02') or __name__ IN UNNEST(@ids), reads each document by its name: the plan is a lookup of the named documents. A bare ID is a document of the FROM collection, and a path such as books/book-01 is accepted too.

use firestore::*;
async fn example(db: FirestoreDb) -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
let rows = db
    .fluent()
    .sql("SELECT title FROM books WHERE __name__ IN UNNEST(@ids)")
    .param("ids", ["book-01", "book-02"])
    .query()
    .await?;
let _ = rows;
Ok(())
}

A read by ID costs 1 read unit for each document of up to 4 KiB, as a Core get does, see Query plans and cost.

A name compared with a column, such as the __name__ of a joined table, is described in Join cost.

SQL names that differ from the pipeline function are renamed: LOWER to to_lower, UPPER to to_upper, POWER to pow, IFNULL to if_null, REGEXP_CONTAINS to regex_contains, AVG to average, MIN to minimum, MAX to maximum, COUNTIF to count_if. SUBSTR, SUBSTRING and STRPOS count from 1 as in SQL, and ILIKE compares both sides in lower case. A SUBSTR position of 0 or below passes to Firestore as written: 0 is the whole string, and a negative position counts from the end with -1 the last character, as in SQL. ORDINAL(0) reads the first element, and a negative ORDINAL or OFFSET counts from the end, where SQL fails or gives NULL. NULLS FIRST and NULLS LAST add a leading sort key that tests for an absent or null value, since Firestore sorts both first in an ascending order.

Search

The search is part of the source, so the translator lifts it out of the WHERE: one document_matches('query') or one geo_distance(..) <= meters that is a top-level AND condition, on a collection or collection group source and before any join. score() AS relevance selects the relevance, and ORDER BY score() DESC or ORDER BY geo_distance(..) as the only sort key becomes the search’s own sort. A search needs a search index, see Search indexes.

A construct with no pipeline form fails with InvalidParametersError that names it, before any request. Anything in a parsed statement that the translator does not map is refused and never dropped, so a statement does not run with a clause missing.

Joins and subqueries

Joins and subqueries are in Preview in Firestore, see Pipeline aggregations and joins. Firestore plans a join as a nested loop: for each row of the left side it runs the right side as a subquery. A subquery in an expression, [NOT] EXISTS, [NOT] IN (SELECT ..), (SELECT ..) or ARRAY(SELECT ..), runs once per row of the query it is in too, whether or not it reads a column of that row, so the rows scanned multiply. Rows scanned and read units on an Enterprise edition database, for an outer collection of 11 documents and an inner one of 300, as Query Explain with analyze reports them:

StatementRows scannedRead units
SELECT title FROM outer111
SELECT n FROM inner3007
SELECT title FROM outer WHERE n IN (SELECT n FROM inner)3,311 (11 + 11 × 300)77
SELECT title FROM outer WHERE (SELECT COUNT(*) AS c FROM inner) > 03,31127
SELECT title FROM outer WHERE EXISTS (SELECT 1 FROM inner WHERE n > 100000)3,31177

The plan of each subquery statement is an Apply of the outer scan to the subquery, so even an uncorrelated COUNT(*) runs once for each outer row.

The cost depends on the index. Without one on the join key, each run reads the whole joined collection. A join or subquery is therefore refused unless the options say .allow_subqueries(), and the error says it runs one subquery per row, see Read-only options. These need no opt-in:

  • a join or subquery into subcollection(..), which reads only the children of each parent;
  • a derived table or a CTE in the FROM of a query, which is the query’s own source and does not multiply with the rows; a JOIN into one is still a join and needs the opt-in;
  • UNNEST of an array of the row.
use firestore::*;
async fn example(db: FirestoreDb) -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
let rows = db
    .fluent()
    .sql(
        "SELECT r.name, v.rating, v.reviewer \
         FROM restaurants AS r LEFT JOIN collection_group('reviews') AS v ON v.restaurant = r.__name__ \
         WHERE r.cuisine = @cuisine",
    )
    .param("cuisine", "breakfast")
    .options(FirestoreSqlOptions::new().allow_subqueries())
    .query()
    .await?;
let _ = rows;
Ok(())
}

Rules for the joined names:

  • a qualified name, v.rating, is a column of the table or alias v, searched from the nearest query outwards, and a table or alias matches without regard to case; an alias used by two tables is an error;
  • a joined table lives in a field named after its alias, and a document can hold a field of any name, so the translation cannot tell whether the alias is the name of a field of the left side. It refuses every way to read such a field instead. In FROM orders AS o JOIN customers AS customer, o.customer is refused, and so is a bare customer in any place but customer IS NULL, since the field customer of the orders is replaced by the joined table. Give the table another alias. A bare alias of an UNNEST names its element, and is allowed;
  • in a query with a join or in a subquery, an unqualified name in an ON clause is an error, since either side could hold it, and so is a dotted name that starts with no table;
  • SELECT * and b.* are refused in a query with a join, for the base table as well as for a joined one. The joined tables would come with the base document’s fields, and replace any of them that has the name of an alias. Name the columns;
  • the anti-join, the left rows that have no match, is WHERE v IS NULL on the alias. WHERE v.rating IS NULL matches nothing, since the field of an unmatched row is absent and not null;
  • a correlated subquery, one that reads a column of the row it runs for, cannot sit in a query that groups, or in a clause with no stage before it to carry the column, such as the SET of an UPDATE;
  • EXISTS (SELECT 1 ..) ignores the select list, so an aggregate, GROUP BY or HAVING inside EXISTS is refused: it would change which rows exist, and the select list that holds it is not evaluated.

A CTE, a named subquery defined with WITH, runs again for each place that uses it: a CTE referenced twice runs twice. Results are not kept or reused between references. A statement that repeats CTE bodies more than 1,024 times in all is refused.

Join cost

Rows scanned and read units for some joins on an Enterprise edition database, as Query Explain with analyze reports them, over small collections: 9 restaurants with 6 reviews, 11 books and 1,500 items.

JoinRows scannedRead unitsResults
9 restaurants to the reviews collection group by a reference field, no index63 (9 + 9 × 6)36
the same, for the 3 restaurants with cuisine = 'breakfast'27 (9 + 3 × 6)23
9 restaurants to subcollection('reviews')15 (9 + 6)16
11 books to books on genre, with the index (genre ASC, rating DESC)26 (11 + 15)1715
20 of 1,500 items to the same 1,500 items on n, no index31,500 (1,500 + 20 × 1,500)86420

The unindexed join scans the joined collection once for each left row: parents × child collection. The indexed join reads an index range for each left row, and a join into subcollection(..) reads each parent’s children only.

Rules that follow from it:

  • index the join key, and run .explain() before the join reaches production data. A plan with a TableScan under the join is the unindexed case, see Query plans and cost;
  • a join that compares the joined table’s __name__ with a column of the left row becomes a lookup by name for each left row. A plain = of __name__ with a variable in a per-row subquery scans the collection instead: over a collection of 60 documents, run for 3 rows, it scans up to 180 rows, where the lookup by name reads 2;
  • a join over a large collection that is run for analysis belongs in BigQuery. Firestore joins fit a left side that a filter has narrowed to a few documents.
